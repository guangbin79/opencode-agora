# F107 提案：verify 门 base-red 探针

> 状态：提案待用户裁决，未裁决不实施。登记：docs/reqs/opencode-agora.md F107（任务 ag-36b2af，2026-11-15）。

## 1. 背景

- verify 门只认「命令绿→合并」，verify_cmd 从不在任务起点 base 上运行——与任务无关、在 base 上本来就绿的空洞 verify 可一路绿到合并（假绿）。
- 现状 gate.py 只用 env_base 拒零提交（`_vacuous_delivered` 判据 (a)），不检验收命令的判别力。
- 对照证据——**验证器双向都会错，先审计验证器本身再谈合并**：
  - SWE-bench FAIL_TO_PASS 纪律：测试须「修前红、修后绿」——修前也绿的测试不证明修复。
  - OpenAI 2026-02 弃用 SWE-bench Verified：难解子集 59.4% 测试有缺陷、拒绝功能正确的解＝**假阴**。
  - ICSE 2026 审计：7.2–8.4% 的 resolved 补丁实为坏补丁＝**假阳**。
- 推论：base-red 探针＝FAIL_TO_PASS 的最小机械近似——验证器在 base 上必须红；base 上也绿，证明它不区分。

## 2. 设计

- 门内复用集成 worktree 机械（`build_integration_at` 同款），在任务起点 base commit（任务行 env_base）上运行一次 verify_cmd。
- 红 → 探针通过放行（verify 有判别力），门流程零变化。
- 绿 → 按分类处理：豁免形态见 §3，处置形态见 §4 裁决点 2。
- 只跑一次：结果缓存于任务行，reopen／崩溃重排不重复探针。

## 3. 豁免分类备选（三案，各列优劣）

| 备选 | 优 | 劣 |
|---|---|---|
| A 建单旗标 `verify_base_exempt`，派发方显式声明 | 意图显式、逐单可控、审计留痕 | 多一个登记参数；派发方习惯性全开＝形同虚设 |
| B 静态判据自动豁免：verify_cmd 仅含 lint、build、全量测试形态＝回归守卫型 | 零登记成本、默认安全 | 文本启发式可被措辞绕过／误伤；且该形态与假绿高危面（笼统 verify）高度重合——恰是本探针要防的对象 |
| C 一律硬拒无豁免 | 规则最简、零特判 | 真回归守卫任务（全量测试守卫单）在 base 上天然绿＝全数误杀 |

## 4. 裁决点（需用户裁定，逐条）

1. 豁免形态选哪个：A／B／C，或组合（B 静态兜底＋A 显式逃生门）。
2. base 绿时硬拒还是警告：硬拒＝空洞 verify 即时挡下（阻塞流水线换真闸）；警告＝审计＋放行（只降噪不设闸）。
3. quick 路是否豁免：quick 验收来自账本历史多数投票，本身已含已验证多数判——倾向豁免，待确认。

## 5. e2e 影响

现有 verify 门用例受影响面（tests/test_core_gate.py，探针在门内新增一次 verify 运行）：

- env／集成 verify 双跑族（F7、F32、F98、F100、F101、F105）：注入 runner 的调用次序与相关断言需适配探针前置运行。
- F36 软硬双顶、F81/F82 命令死分类：探针自身运行的死类／超时分类语义需定义（探针死≠活差，不得误弹 worker）。
- 零提交探针族（F69、ag-1ae0f1）：env_base 语义扩展点重合，需防判定互扰。
- tests/e2e/multi_instance_delivery.py：verify 均为真实命令，逐场景需复核 base 上的红绿形态。

需补用例清单（先红后绿）：

- base 红放行：探针通过，门流程零变化。
- base 绿拒：按裁决点 2 选定形态断言。
- 豁免三态：旗标豁免放行／静态判据豁免放行／无豁免照拒（按 §4 裁决 1 选定形态）。
- 探针运行命令死／超时：不误弹 worker、分类路由到派发方。
- reopen 重跑不重复探针（缓存生效）。

## 6. 备选方案与否决理由

- 变异测试（直接测验证器判别力）：Meta 工业规模明说跑不动——单机单开发者更不可行。
- 训练型验证者模型（LLM 判 verify 有效性）：SWE-Critix 负例 recall 64%——三成多漏判，不够格当合并门。
- SMT 需求一致性检查（spec↔verify 形式化对齐）：goal 为自由文本，机械无抓手。
